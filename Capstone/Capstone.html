4. Si lidhet Frontend me Backend

Frontend nuk flet direkt me PostgreSQL. Gjithçka kalon te API përmes frontend/lib/api.ts.

// frontend/lib/api.ts — klienti i vetëm i API-së
fetch(`${BASE}/api/v1${path}`, {
  credentials: "include",   // dërgon cookies httpOnly automatikisht
  headers: { "Content-Type": "application/json" },
  ...init,
})

Auto-refresh në 401

API call → merr 401 Unauthorized (access token skaduar)
Thërret POST /auth/refresh me cookie refresh_token
Backend kthen access + refresh token të ri (cookies të reja)
Riprovan kërkesën origjinale një herë
Nëse refresh dështon → error, redirect te login

Auth Context (lib/auth-context.tsx)

  • Ngarkon app → thërret GET /auth/me automatikisht
  • Ruan gjendjen: loading | authenticated | unauthenticated
  • logout() → POST /auth/logout → redirect /login
  • refreshUser() → thirret pas login-it të suksesshëm

6. Autentifikimi — Hap pas Hapi

6.1 Regjistrimi

Frontend: /register → formë: email, password, full_name

Backend: POST /api/v1/auth/register

Kontrollon nëse email ekziston → 400 "Email already registered"
hash_password() me bcrypt — password nuk ruhet kurrë plaintext
Krijon user me role="customer" — hardcoded, jo nga body!
Schema UserCreate nuk ka fushë role — klienti s'mund ta dërgojë
Commit në DB → kthen UserRead (pa password)

6.2 Login

Frontend: /login → dërgon email + password

Backend gjen user me email
verify_password() me bcrypt
Gabim → 401 "Invalid email or password" (mesazh i njëjtë — anti user-enumeration)
Sukses → krijon 2 JWT tokens
I vendos si httpOnly cookies
Frontend: refreshUser() → redirect sipas rolit
Roli pas loginRedirect
agent/tickets/queue
customer, admin/tickets

6.3 JWT & Cookies

TokenJetëgjatësiaCookie pathPërdorimi
access_token15 minuta/Autorizon çdo API call
refresh_token7 ditë/api/v1/authRinovon access token

JWT Payload:

{
  "sub": "3",              // user id
  "role": "customer",
  "email": "user@example.com",
  "type": "access",        // ose "refresh"
  "iat": 1719000000,
  "exp": 1719000900
}

Cookie attributes: httponly=True, samesite=lax, secure (prod HTTPS)

Pse httpOnly? JavaScript NUK i lexon cookies httpOnly → edhe nëse ka XSS, attacker-i s'mund të vjedhë token-in (ADR-001).

6.4 Refresh & Logout

Refresh: POST /auth/refresh — lexon cookie refresh_token, verifikon, krijon çift të ri tokens, i vendos si cookies.

Logout: POST /auth/logout — fshin të dy cookies (delete_cookie).

get_current_user() — çdo API i mbrojtur

Lexon cookie access_token — nuk ka? → 401
decode_token() — verifikon signature, expiry, type="access"
Token i pavlefshëm → 401
Kthen _UserStub(id, role, email) — identiteti vetëm nga JWT

7. Siguria — RBAC + IDOR

Niveli 1: RBAC (Route-level)

A lejohet roli të thërrasë këtë endpoint?

# Vetëm admin
require_roles("admin")

# Vetëm agent (p.sh. GET /tickets/queue)
require_roles("agent")

# Admin router — guard në nivel router (admin.py)
router = APIRouter(dependencies=[Depends(require_roles("admin"))])

Niveli 2: Object-level (IDOR Defense)

A lejohet ky user të shohë këtë rresht specifik?

flowchart TD
    REQ["GET /tickets/5"] --> AUTH["get_current_user()"]
    AUTH --> FIND["Gjej ticket id=5"]
    FIND --> ACCESS{"can_access_ticket()?"}
    ACCESS -->|"customer: requester_id==user.id"| OK["200 + data"]
    ACCESS -->|"agent: assignee_id==user.id"| OK
    ACCESS -->|"admin: always"| OK
    ACCESS -->|"else"| DENY["403 Forbidden"]
RolKushti SQLShembull
customerrequester_id == user.idSheh vetëm biletat e veta
agentassignee_id == user.idSheh vetëm biletat e caktuara
adminPa filterSheh gjithçka
Demo IDOR për mbrojtje: Login si customer → provo GET /tickets/1 (bileta e dikujt tjetër) → 403 Forbidden. Integer PK (1,2,3...) por siguria vjen nga autorizimi, jo fshehtësia e ID-së.

Golden Rules

  1. Identiteti (user.id, role) vjen nga JWT — kurrë nga request body
  2. Role whitelisted nga UserCreate — klienti s'mund të self-promovohet
  3. RBAC (roli lejohet?) AND ownership (sheh këtë rresht?) — të dyja kontrollohen
